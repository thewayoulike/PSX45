# PSX45 project audit

**Implementation update:** A01–A10 have local fixes and regression coverage. See [implementation and required rollout](audit-a01-a10-implementation.md). The findings below preserve the original audit; production rollout is still pending.

Reviewed September 14, 2026. Scope: local application source, alert APIs/storage, access rules, Drive/Sheets persistence, selected calculations, build configuration and tests. This is a targeted engineering audit, not an exhaustive review of every component or a production penetration test. No live accounts, database records, emails or push notifications were accessed or modified.

## Executive assessment

The application builds successfully and its current-checkout utility tests pass. The highest-priority work is enforcing alert ownership, preventing silent cloud-save failures, and making concurrent alert updates safe. Passing utility tests currently provides little evidence about these integration paths.

Priorities: **P1** = address before expanding usage; **P2** = next reliability sprint; **P3** = maintenance/backlog. Findings below distinguish direct code evidence from locally reproduced behavior. Effort is relative: S = localized change, M = coordinated changes/tests, L = architecture or data migration.

## Findings and proposed fixes

### A01 — P1: Alert APIs do not enforce record ownership [M]

**Evidence:** [get-alerts.js:21](../api/get-alerts.js#L21), [delete-alert.js:22](../api/delete-alert.js#L22), [save-alert.js:52](../api/save-alert.js#L52), [alertsStore.js:25](../lib/alertsStore.js#L25).

The API authenticates the requester, then selects an alert record using only the supplied push endpoint. Listing and deleting never compare the record owner with the authenticated user; saving overwrites `record.userEmail`. Storage uses a service-role client, so application ownership checks are essential.

**Trigger/impact:** A second signed-in user who has another user's endpoint can read or modify that record. A shared browser/subscription across account changes is also a plausible trigger. Endpoint discovery is a prerequisite; this is not a claim that all records are publicly enumerable.

**Fix:** Store a stable owner identifier and enforce it on every operation, preferably in transactional database functions. Define a migration policy for ownerless records and account switching.

**Acceptance:** User B receives 403 for list/delete/save against A's record, while A succeeds; ownerless records cannot be claimed simply by supplying their endpoint.

### A02 — P1: Unapproved users and failed quota lookups receive paid alert limits [S–M]

**Evidence:** [save-alert.js:6](../api/save-alert.js#L6), [requireOnlineUser.js:27](../lib/requireOnlineUser.js#L27).

Only `plan === 'free'` selects free limits. A pending account therefore receives paid limits, and the exception handler also returns paid limits. The route checks sign-in but not approval. The Supabase query error is not explicitly handled.

**Trigger/impact:** An authenticated but unapproved user calls the route directly, or the access lookup fails. The UI approval gate does not protect this API.

**Fix:** Reject pending access; distinguish a missing access row from an infrastructure error; return a retryable failure when access cannot be established. Calculate quotas only after authorization succeeds.

**Acceptance:** Pending users cannot create alerts; lookup failures never grant extra entitlements; free/trial/paid/lifetime cases each have route tests.

### A03 — P1: Cloud save failures are silently treated as completion [M]

**Evidence:** [driveStorage.ts:231](../src/services/driveStorage.ts#L231), [driveStorage.ts:255](../src/services/driveStorage.ts#L255), [App.tsx:1716](../src/components/App.tsx#L1716).

`saveToDrive` does not inspect the upload response and catches errors without propagating a result. Missing tokens also return normally. The caller then clears the syncing state. Sheets writes similarly omit response checks.

**Trigger/impact:** A 401, 403, 429, server error or network failure leaves remote data stale without a durable failed-save state. Users may assume their portfolio has been backed up. This does not imply local data is immediately lost.

**Fix:** Return a typed success/failure result, validate every response, retain unsynced revisions, and display last successful save plus retry status. Serialize saves to prevent an older request from finishing after a newer one.

**Acceptance:** Mock each failure type; no failure advances the last-saved revision; retry preserves the latest state; concurrent saves cannot overwrite newer data with older data.

### A04 — P1: Whole-record alert writes can lose updates or duplicate delivery [M–L]

**Evidence:** [alertsStore.js:46](../lib/alertsStore.js#L46), [save-alert.js:52](../api/save-alert.js#L52), [run-alerts.js:73](../api/run-alerts.js#L73), [delete-alert.js:22](../api/delete-alert.js#L22).

Each operation reads a JSON record and later replaces or deletes it without a version precondition. Separating records by device protects different devices, but not simultaneous operations on the same device.

**Trigger/impact:** Two saves read the same version and one overwrites the other. A cron run can overwrite an alert added after its read, or delete the entire record after a new alert was added. Overlapping cron runs can both send the same notification. These are code-derived race scenarios, not live reproductions.

**Fix:** Normalize alerts into rows and use transactional mutation/claim operations, or implement versioned compare-and-swap with retries. Add delivery claim/idempotency state.

**Acceptance:** Deterministically interleave save/save, save/cron and delete/cron; no unrelated alert disappears and only one worker claims a delivery.

### A05 — P2: Sheets tab names can collide and overwrite another portfolio [M]

**Evidence:** [driveStorage.ts:346](../src/services/driveStorage.ts#L346), [driveStorage.ts:372](../src/services/driveStorage.ts#L372).

Tab identity is derived from the sanitized, truncated portfolio name. For example, `A/B` and `A:B` both become `A_B`. Both sync operations then clear and write the same tab. The initial `existingTitles` set is also not updated after tab creation. Quoted A1 ranges do not escape apostrophes in names.

**Fix:** Persist a portfolio-ID-to-sheet-ID mapping; use display names only as labels. Handle renames and escape/encode ranges. Avoid clearing existing data until the replacement can be safely applied.

**Acceptance:** Colliding names, names longer than 100 characters, apostrophes and renames retain separate portfolio data; failed replacement does not leave a cleared export.

### A06 — P2: Trials renew indefinitely when approval dates are missing [S]

**Evidence:** [access.js:79](../lib/access.js#L79).

`computeAccess` uses the current time as the trial start whenever `approved_at` is absent. This fallback is not persisted, so each request starts another trial window.

**Local reproduction:** For `{approved: true}`, advancing the clock by 30 days still returned `plan: 'trial'`; the trial end also moved forward 30 days.

**Fix:** Backfill approval dates once using an explicit migration policy. Keep access computation pure with a fixed persisted start, or explicitly classify legacy users as lifetime if that is intended.

**Acceptance:** A legacy user's trial end stays fixed across repeated calls and expires at the agreed time.

### A07 — P2: XIRR reports a numeric result without convergence [S–M]

**Evidence:** [finance.ts:50](../src/utils/finance.ts#L50), [finance.ts:60](../src/utils/finance.ts#L60).

The solver returns the final rate even after a zero derivative or failed convergence. It does not require a valid root before displaying a percentage.

**Local reproduction:** Cash flows of -100 and +110 on the same date return **10%**, the default guess. Discounting cannot change their net amount, so this input has no XIRR solution.

**Fix:** Return an explicit unavailable/non-convergent result, validate finite amounts, and use a bounded fallback solver when appropriate. Make the UI distinguish zero return from an undefined return.

**Acceptance:** Cover same-day unequal flows, one-sign flows, ordinary one-year returns, near-total losses, non-finite inputs and solver failure.

### A08 — P2: Missing cron configuration bypasses its authorization check [S]

**Evidence:** [run-alerts.js:57](../api/run-alerts.js#L57).

If both the configured secret and supplied query secret are absent, `undefined !== undefined` is false and execution continues. The impact is conditional on the rest of the service being configured; production configuration was not inspected.

**Fix:** Reject missing server configuration explicitly and require a nonempty credential, preferably in an Authorization header. Update the scheduled caller together with the route.

**Acceptance:** Missing/mismatched credentials never reach alert storage or dispatch; valid credentials do. Ensure scheduler failures surface as failed jobs rather than relying on curl's default treatment of HTTP errors.

### A09 — P2: Quota counters are scoped to a browser or subscription, not an account [M]

**Evidence:** [freemiumQuotas.ts:3](../src/utils/freemiumQuotas.ts#L3), [save-alert.js:51](../api/save-alert.js#L51).

Browser quota keys do not contain a user ID. Two free accounts sharing a browser therefore share consumption, while another browser or cleared local storage starts fresh. Alert ticker limits are counted within one subscription, so additional devices provide additional allowances.

**Fix:** Decide explicitly whether limits are account-wide or device-wide. For account-wide entitlements, use server-side atomic counters keyed by user and Karachi calendar day; namespace local caches by account. If browser limits are intentionally soft, document that limitation.

**Acceptance:** Account switching does not inherit another user's consumption; multi-device usage follows the selected policy; clearing a cache cannot reset a hard server quota.

### A10 — P2: Backtest results omit gap execution and open-trade drawdown [M]

**Evidence:** [strategyBacktest.ts:104](../src/utils/strategyBacktest.ts#L104), [strategyBacktest.ts:139](../src/utils/strategyBacktest.ts#L139).

Stops execute at the stop price whenever the daily low crosses it, even if the entire bar trades below that price. For example, a stop at 98 with the next bar opening at 90 and reaching only 92 still exits at 98. Drawdown is computed only from closed-trade returns, omitting losses while a position remains open.

**Fix:** Define gap-aware fill rules and track daily marked-to-market equity. If retaining simplified calculations, label drawdown as closed-trade drawdown and disclose the execution assumptions in the result.

**Acceptance:** Synthetic gap bars cannot fill at unavailable prices; a recovering position's interim loss appears in daily drawdown. Include fees consistently in equity and comparison metrics.

| Rank | Addition | User value | First acceptance milestone | Effort |

## Recommended implementation sequence

1. **Protect accounts and persistence:** A01–A04 and A08, with route/storage tests.
2. **Correct deterministic behavior:** A05–A07 and A09–A10, with focused regression cases.
3. **Establish repeatable checks:** test isolation, typecheck/CI and repository hygiene.
4. **Improve product trust:** sync recovery, alert history and freshness indicators.
5. **Optimize and expand:** initial bundle reduction, import reconciliation and backtest controls.
